# LSP (Liskov Substitution Principle) 實作分析

本文件對 `solid/lsp/` 下的 `bad-implementation.cpp` 與 `good-implementation.cpp` 進行對比分析，探討其對 **里氏替換原則 (LSP)** 的符合程度。

---

## 1. 錯誤實作 (`bad-implementation.cpp`)

在此實作中，`Square` 繼承自 `Rectangle`。這雖然符合幾何學上的「正方形是長方形的一種」，但在軟體行為建模中是一個典型的 **LSP 違反** 案例。

### 違反 LSP 的原因：
*   **行為契約破壞**：基底類別 `Rectangle` 的契約暗示 `set_width` 與 `set_height` 是獨立的行為（修改一個不應影響另一個）。
*   **非預期的副作用**：`Square` 為了維持其特性，覆寫方法時導致屬性聯動，破壞了父類別的邏輯假設。
*   **結論**：`Square` 物件無法在不改變程式正確性的前提下，替換掉其基底類別 `Rectangle`。

---

## 2. 正確實作 (`good-implementation.cpp`)

在此實作中，不再使用繼承關係，而是讓兩者共同實作一個更抽象的介面 `Shape`。

### 符合 LSP 的原因：
*   **提取共同行為**：`Shape` 介面僅定義了 `area()`，這是一個行為一致且無副作用的契約。
*   **職責分離**：`Rectangle` 保留其寬高獨立性，`Square` 專注於單一邊長。兩者互不干涉。
*   **結論**：子型別（`Rectangle`, `Square`）可以安全地替換其基底型別（`Shape`）。

---

## 3. 核心差異總結

| 特性 | 錯誤實作 (Bad) | 正確實作 (Good) |
| :--- | :--- | :--- |
| **繼承結構** | `Square` -> `Rectangle` | 兩者 -> `Shape` |
| **替換安全性** | **低** (會導致邏輯錯誤) | **高** (符合多型預期) |
| **符合 LSP** | **否** | **是** |

---

## 4. 《Software Architecture with C++》理論要點

根據書中第 1 章的探討，關於 LSP 有幾個核心觀念值得注意：

*   **定義**：如果一個函式使用基底類別的指標或引用，那麼該函式必須能夠在不知情的情況下，使用衍生類別的物件。
*   **抽象的誤區**：LSP 經常被違反，是因為我們在原始碼中應用的技術（如繼承）並不總是適用於現實世界的抽象。
*   **數學 vs. 軟體行為**：數學上正方形是長方形的特化（is-a），但在軟體建模中，如果基底類別定義了寬高可獨立變動的行為，這種繼承就會產生「概念性錯誤」。
*   **解決之道**：當程式碼違反 LSP 時，通常意味著使用了**錯誤的抽象**。書中建議透過實作共通的介面（如 `Shape`）來解決，而非強制建立繼承關係。

---

## 總結

LSP 提醒我們：**繼承應基於行為（Behavior）的相容性**。如果子類別改變了基底類別原有的邏輯假設，則繼承關係是錯誤的。建議 **提取介面** 或 **改用組合**。
